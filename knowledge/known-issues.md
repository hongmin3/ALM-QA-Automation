# Known Issues

## 렌더링 무한폭주 버그 — 원인을 못 찾은 문제를 "자동 격리"로 우회한 사례
<!-- akela: id=render-runaway-bug -->

실제 운영 데이터로 테스트하던 중, 특정 SRS 하나가 포함된 그룹만 PDF 생성에 20분 넘게 걸리고 30,000페이지가 넘는 PDF가 나오는 현상이 발생했다(정상 범위는 100~200페이지). 같은 그룹의 다른 항목들은 전혀 문제가 없었다.

### 진단 과정과 한계

1. 이미 생성된 HTML을 재사용해(Polarion 재수집 없이) 항목을 절반씩 나눠 렌더링 시간을 비교하는 이분 탐색으로 정확히 SRS 1건까지 범위를 좁혔다.
2. 해당 SRS의 Rich Text를 뜯어보니 스펙에 어긋나게 깊이 중첩된 목록 구조, 실제 크기와 다르게 강제 지정된 이미지 크기 등 의심 요소가 여럿 발견됐다.
3. 의심 요소를 하나씩 제거하며 재테스트했지만 어느 것도 단독 원인이 아니었다(테스트 1회당 최대 22분 소요).
4. **Chromium 인쇄 페이지네이션 엔진 내부의 특정 조합에서 발생하는 문제로 추정되나, 정확한 트리거 요소는 끝내 특정하지 못했다.**

### 채택한 원칙 — "원인을 몰라도 안전하게 동작하게 만들기"

원인 규명에 매달리는 대신 다음 원칙으로 방향을 바꿨다: *"어떤 SRS가 문제를 일으키는지는 몰라도, 문제를 일으키는 SRS가 있다는 사실 자체는 렌더링 시간으로 감지할 수 있다."*

- PDF 렌더링을 별도 프로세스로 격리하고 시간제한(90초)을 둔다. 초과하면 자식 프로세스(브라우저 포함)까지 프로세스 트리 전체를 강제 종료한다.
- 그룹 전체 렌더링이 시간 초과되면, 수동으로 하던 이분 탐색을 그대로 자동화해 문제 SRS를 찾아낸다(레코드를 절반씩 나눠 재귀적으로 렌더링 재시도).
- 문제 SRS를 찾아도 **문서에서 제외하지 않는다.** 대신 렌더링을 멈추게 하는 것으로 추정되는 복잡한 서식(중첩 구조 등)만 제거하고, 본문 텍스트와 이미지는 그대로 보존한 안내 배너 포함 블록으로 대체한 뒤 전체 그룹을 다시 정상 렌더링한다.
- 어떤 SRS가 격리되었는지는 로그와 변경 리포트에 명시적으로 남긴다(조용히 넘어가지 않음). 필요하면 사람이 원본을 직접 확인할 수 있게 한다.

### 반복 탐색을 피하되 수정 반영은 놓치지 않는 캐시 설계 (`src/problem_state.py`)

이분 탐색은 문제 SRS 1건을 찾는 데 약 10분이 걸린다. 주간 자동 실행이므로, 원인을 이미 아는 SRS를 매주 다시 찾는 것은 순수한 낭비다. 그렇다고 단순히 "이 SRS는 문제니까 건너뛴다"는 목록 캐시로만 관리하면, 그 사이 원본이 수정되어 정상 렌더링이 가능해졌어도 계속 서식이 낮은 상태로 남는 새로운 문제가 생긴다.

그래서 **목록 캐시가 아니라 본문 해시 기반 캐시**로 구현했다:

- 문제로 확인한 시점의 **본문 SHA-256**과 **렌더링 파이프라인 SHA-256**을 함께 저장.
- 다음 실행에서 둘 다 같으면 이분 탐색을 생략(약 10분 절약).
- 본문 해시가 다르면 캐시를 무시하고 정상 렌더링부터 다시 확인 — 원본 수정으로 문제가 해소됐을 가능성을 놓치지 않는다.
- 렌더링 파이프라인 해시가 다르면(HTML 템플릿/CSS 또는 Playwright 인쇄 옵션 변경) 역시 전부 재확인 — 본문이 그대로여도 파이프라인 개선으로 폭주가 해소될 수 있는데, 본문 해시만 봤다면 그 개선이 영구히 반영되지 않는 문제를 막는다.
- 재확인 결과 정상 렌더링되면 캐시 상태에서 자동 제거하고, 설정(`render.known_problem_srs`)에서 빼도 된다고 로그로 안내한다.
- `--recheck-known-problems`로 언제든 캐시를 무시한 전체 재확인이 가능하다.

**중요한 범위 제한**: SRS 본문의 수집·Snapshot 저장·변경 리포트 생성은 이 캐시와 **무관하게 항상** 수행된다. 캐시가 영향을 주는 범위는 "PDF 안에서 서식을 단순화할지 여부"로만 한정되어 있다.

### 일반화 가능한 패턴

완벽한 근본 원인 분석이 항상 가능하거나 시간 대비 효율적이지 않을 때: **감지 → 격리 → 최소 손실 복구 → 캐시하되 무효화 조건을 명시**로 시스템을 견고하게 만드는 실용적 패턴. 유사한 "간헐적이고 재현이 어려운 외부 엔진/라이브러리 버그"에 적용 가능한 접근이다.

### 관련 설정 (config `render:` 블록)

| 키 | 기본값 | 설명 |
|---|---|---|
| `pdf_timeout_seconds` | 300 | PDF 렌더링 1회 시도의 시간제한. 정상 그룹은 대화형 40~70초, 스케줄러(저우선순위)에서는 더 오래 걸릴 수 있다. 폭주 케이스는 16분 이상이므로 이 값으로 걸러진다. |
| `known_problem_srs` | (빈 목록) | 렌더링 폭주가 확인된 SRS의 `프로젝트/ID`. 등록하면 이분 탐색을 생략한다(무효화 조건은 위 캐시 설명 참고). |
