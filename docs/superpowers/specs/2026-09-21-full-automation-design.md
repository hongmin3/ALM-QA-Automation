# ALM QA 완전 자동화 설계

## 목표

평일 오전 09:00에 SRS와 이슈를 순서대로 수집하고, 두 결과가 완전한 경우에만 변경 영향과 검토 우선순위를 계산한다. 새 검토 후보와 실행 실패는 영속 대기함에 먼저 저장한 뒤 기존 SRS SMTP 설정으로 이메일을 발송한다. 같은 변경은 한 번만 알리고, 발송 실패는 다음 실행에서 재시도한다.

프로그램은 Polarion을 조회만 한다. 이슈 수정, 자동 승인, 외부 AI API 호출은 하지 않는다. 실제 설정·원문·생성물·실행 상태는 Git에서 제외한다.

## 선택한 접근

기존 SRS와 이슈 앱을 그대로 유지하고 루트에 통합 오케스트레이션 계층을 추가한다. 오케스트레이터는 각 앱을 별도 프로세스로 실행하고 manifest와 스냅샷을 통해 결과를 받는다.

두 앱의 내부 수집·렌더링 코드를 공통 라이브러리로 재작성하지 않는다. 이 방식은 이미 검증한 앱의 작업 디렉터리, 설정 형식, 종료 코드와 복구 정책을 유지하면서 통합 실행 이력과 알림을 독립적으로 시험할 수 있다.

## 구성 요소

| 구성 요소 | 책임 |
|---|---|
| `automation.py` | CLI, 단일 실행 잠금, 단계 실행, 재시작 판단, 최종 종료 코드 |
| `automation_core/config.py` | 공개 예시 설정 로드와 경로·중요도·재시도 정책 검증 |
| `automation_core/orchestrator.py` | SRS → 이슈 → 분석 → 대기함 → 발송의 순차 실행과 manifest 작성 |
| `automation_core/correlation.py` | 명시적 Polarion 링크와 항목 ID에 근거한 SRS–이슈 연계 및 중요도 계산 |
| `automation_core/state.py` | 실행 manifest, 후보, 대기함의 잠금·원자적 저장·중복 방지 |
| `automation_core/email.py` | 기존 SRS SMTP 설정 로드, 최소 정보 이메일 생성, 대기 메시지 발송 |
| `automation.example.yaml` | 실행 주기 외 정책, 중요도 매핑, 알림 임계값의 공개 예시 |
| `scripts/install_automation_task.ps1` | 평일 09:00 통합 작업 설치·미리보기·기존 SRS 작업 비활성화 |

## 실행 흐름

1. 오케스트레이터가 `.automation/.lock`의 OS 잠금을 획득하고 UTC 기반 실행 ID를 만든다.
2. 이전 실행에서 `PENDING`인 이메일을 제한 횟수 내에서 먼저 재시도한다.
3. SRS 앱을 기존 작업 디렉터리에서 새 `--no-mail` 옵션으로 실행한다. 이 옵션은 수집·검증·배포 동작은 유지하고 기존 개별 결과 메일만 억제한다.
4. SRS가 성공하면 런타임에 SRS 설정 로더를 사용해 오늘 스냅샷 경로를 확인한다. 설정값이나 원문은 통합 로그에 출력하지 않는다.
5. 이슈 앱을 기존 설정 쿼리로 실행하되 출력은 `.automation/collections/<run-id>/issues`로 고정한다.
6. 이슈 manifest가 `SUCCESS`이고 건수·중복·경고·PDF 조건을 통과한 경우에만 분석한다.
7. 기존 관찰 상태와 비교하여 신규·변경 후보를 만들고, 명시적 링크로 SRS와 이슈를 결합한 뒤 중요도를 계산한다.
8. 새 알림 내용을 먼저 outbox에 원자적으로 저장한다. 저장 성공 후에만 SMTP 발송을 시도한다.
9. 실행 manifest를 확정하고 잠금을 해제한다.

SRS 또는 이슈 단계가 실패하면 후속 분석으로 진행하지 않는다. 이전 후보와 기준선은 변경하지 않고 실패 알림만 대기함에 추가한다.

통합 상태에 이전 성공 입력이 없는 첫 실행은 기준선만 저장하고 기존 전체 항목을 신규 후보로 알리지 않는다. 이후 실행부터 이전 기준선과 달라진 항목만 후보로 만든다.

## 연계와 중요도 규칙

연계는 SRS 또는 이슈가 가진 명시적 linked work item ID와 본문/구조화 필드에 있는 정확한 Polarion ID 참조만 사용한다. 제목 유사도, 임베딩, 키워드 유사도는 사용하지 않는다. 후보에는 사용한 링크 방향과 ID를 근거로 기록한다.

기본 중요도는 다음과 같다.

| 중요도 | 기본 조건 |
|---|---|
| `CRITICAL` | 변경 SRS와 연결된 이슈가 재오픈 상태이거나 blocker/critical 등 설정된 최상위 심각도 |
| `HIGH` | 변경 SRS와 연결된 미해결 이슈 |
| `MEDIUM` | 연결되지 않은 SRS 변경 또는 신규·변경 이슈 |

상태·심각도 문자열은 `automation.example.yaml`에서 프로젝트별 값으로 교체할 수 있다. 알 수 없는 값은 심각도를 높여 추정하지 않고 `MEDIUM`으로 보존한다. 자동 삭제 후보는 만들지 않는다.

후보 식별자는 소스, 프로젝트, 항목 ID, 변경 전후 해시, 연결된 ID 집합을 정규화하여 계산한다. 같은 식별자는 재실행해도 새 후보나 이메일을 만들지 않는다. 사용자가 지정한 `NEW`, `IN_REVIEW`, `DONE`, `EXCLUDED` 상태는 후속 수집에서도 유지한다.

## 실행 상태와 저장 형식

`.automation/`은 Git 제외 운영 상태다.

```text
.automation/
  state.json
  outbox.json
  .lock
  runs/<run-id>/manifest.json
  runs/<run-id>/summary.md
  collections/<run-id>/issues/...
```

`state.json`이 후보와 마지막 성공 입력의 확정 기록이다. `outbox.json`은 `PENDING`, `SENDING`, `SENT`, `FAILED` 상태, 시도 횟수, 다음 시도 시각, 내용 해시를 저장한다. 발송 직전에 SENDING을 확정하고 정상 반환 뒤 SENT 또는 PENDING을 기록한다. SENDING 상태에서 프로세스가 종료되면 SMTP 수신 여부를 알 수 없으므로 자동 재전송하지 않고 수동 확인·재대기 대상으로 남긴다. 쓰기는 같은 디렉터리의 임시 파일을 flush/fsync한 뒤 `os.replace`로 확정한다. 프로세스가 중단되어 참조되지 않는 run/collection 폴더가 남을 수 있으며, 다음 실행은 확정 상태 파일만 신뢰한다.

기존 `.observation/state.json`이 있으면 최초 통합 실행 때 후보와 검토 상태를 schema version 2로 복사해 가져온다. 원본 `.observation`은 삭제하거나 수정하지 않는다. 이후 `observation.py`도 공통 상태 모듈을 사용해 수동 관찰과 예약 실행이 같은 후보 상태를 보게 한다.

실행 manifest는 단계별 `NOT_RUN`, `SUCCESS`, `PARTIAL`, `FAILED`와 종료 코드, 입력 manifest 경로, 후보 수, 알림 상태를 기록한다. 원문, 토큰, SMTP 비밀번호, 서버 오류 전문은 기록하지 않는다.

## 이메일 정책

SMTP host, 계정, 수신자, TLS, 비밀번호는 기존 SRS `mail` 설정과 환경변수 로더를 재사용한다. 새 자격증명 형식을 만들지 않는다.

메일은 원문 전체나 첨부파일을 포함하지 않는다. 다음 정보만 포함한다.

- 실행 성공/실패와 단계별 상태
- 신규 후보의 중요도, 프로젝트/항목 ID, 선정 이유
- 연결된 SRS/이슈 ID와 상태 변화
- 로컬 summary 경로

정상 요약은 새 `CRITICAL`, `HIGH`, `MEDIUM` 후보가 있을 때 한 통으로 묶는다. 데이터 단계 실패는 별도 실패 메시지로 큐에 넣는다. SMTP 오류는 데이터 실행을 되돌리지 않으며, 최대 3회까지 다음 실행에서 재시도한다. 3회 실패한 항목은 `FAILED`로 남겨 수동 재전송할 수 있게 한다. 내용 해시가 같은 항목은 상태와 관계없이 중복 생성하지 않는다. SMTP가 메시지를 받은 직후 프로세스가 종료되는 경계에서는 자동으로 전달 여부를 확정할 수 없으므로 SENDING을 유지하며 운영자가 받은 편지함을 확인한 뒤 SENT 확정 또는 수동 재대기한다.

## 예약 작업 전환

새 작업 이름은 `ALM_QA_Automation_Daily`이고 월요일부터 금요일까지 오전 09:00에 실행한다. `StartWhenAvailable`, 네트워크 필요, `IgnoreNew`, 제한 실행 시간, 보통 우선순위를 적용한다. 놓친 실행은 Windows Task Scheduler가 다음 가능 시점에 한 번 시작한다.

설치 스크립트는 기본적으로 계획만 출력하는 `-WhatIf`를 제공한다. 실제 설치에서는 다음 순서를 지킨다.

1. Python 경로와 통합 프로젝트 경계를 검사한다.
2. `automation.py --check-local`을 실행한다.
3. 기존 관련 작업 정의를 XML로 `.migration/scheduled-tasks/`에 백업한다.
4. 새 작업을 등록하고 action, working directory, trigger, settings를 다시 읽어 대조한다.
5. 새 작업이 올바른 경우에도 기존 작업은 유지한다. 첫 통합 데이터 실행이 성공한 manifest를 만든 뒤 `-FinalizeTransition`을 실행한 경우에만 기존 `VXvue_SRS_Spec_Automation`과 `_CatchUp`을 비활성화한다.

기존 작업은 삭제하지 않는다. 등록·대조 또는 첫 통합 실행이 실패하면 기존 작업 상태를 유지한다. 첫 통합 성공 전까지 월요일 07:00 기존 작업과 09:00 통합 작업이 같은 날 실행될 수 있으나, SRS 앱은 오늘 스냅샷을 재사용하고 통합 실행은 `--no-mail`을 사용하여 재수집·중복 개별 메일을 피한다.

## 오류와 재시도

- 설정 오류는 외부 연결 전에 종료 코드 2로 끝낸다.
- SRS 또는 이슈 필수 단계 실패는 종료 코드 1이며 분석 기준선을 갱신하지 않는다.
- 수집은 성공했지만 이메일이 대기 중이면 데이터 실행은 보존하고 종료 코드 4로 구분한다.
- 동일 날짜에 이미 데이터 성공 실행이 있고 미발송 메일만 남은 경우 재실행은 수집을 반복하지 않고 outbox만 처리한다.
- 다른 실행이 잠금을 보유하면 종료 코드 4로 끝내며 새 실행 기록이나 알림을 만들지 않는다.
- 네트워크 재시도는 기존 앱 정책을 유지하고, 오케스트레이터가 무제한 재수집하지 않는다.

## 검증 전략

모든 제품 동작은 테스트를 먼저 실패시킨 뒤 구현한다. 테스트는 합성 스냅샷·manifest와 주입 가능한 프로세스/SMTP 대역을 사용하며 실제 서버나 메일을 호출하지 않는다.

- 오케스트레이션: 단계 순서, 앞 단계 실패 시 중단, 재실행 시 수집 생략, 단계별 manifest.
- 연계: 양방향 링크, 정확한 ID만 연결, 상태·심각도 우선순위, 알 수 없는 값, 중복 후보와 검토 상태 유지.
- 대기함: 원자적 저장, 내용 해시 중복 방지, 발송 성공, 실패 후 다음 실행 재시도, 3회 후 FAILED, 중단 복구.
- 보안: 원문·비밀값이 summary/outbox에 들어가지 않으며 실제 설정이 Git에 포함되지 않음.
- 예약: `-WhatIf` 출력, 평일 09:00, 통합 경로, 첫 통합 성공 manifest 전 기존 작업 비활성화 금지.
- 회귀: 기존 전체 테스트, SPEC lint, 실제 합성 CLI 실행, 실제 Chromium PDF smoke test.

실제 작업 등록 후에는 Task Scheduler 정의를 읽어 비교한다. 실제 Polarion 전체 수집과 SMTP 도착 확인은 보호된 운영 설정을 코드나 보고서에 노출하지 않는 별도 운영 검증으로 기록한다.

## 완료 조건

- 통합 CLI가 SRS·이슈·분석·대기함·메일 단계를 단계별 manifest와 함께 실행한다.
- 불완전 수집이 후보 기준선을 갱신하거나 정상 요약 메일을 만들지 않는다.
- 명시적 링크 기반 후보와 기본 중요도가 재현 가능하다.
- 같은 변경과 같은 이메일은 일반 재실행에서 중복 생성·발송되지 않는다. SMTP 응답 확정 전 프로세스 중단은 SENDING으로 남겨 자동 중복 발송을 막는다.
- SMTP 실패 후 재시도와 수동 재전송 경로가 있다.
- 평일 09:00 통합 작업을 안전하게 설치하고 기존 작업을 복구 가능하게 비활성화한다.
- 합성 자동 테스트와 로컬 실행 검증을 통과한다.
- 실제 서버 수집·SMTP 수신을 수행하지 않았다면 이를 완료로 표시하지 않는다.
