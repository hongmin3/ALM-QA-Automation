# automation-workspace 개선 요청 프롬프트

아래 내용을 automation-workspace 프로젝트의 새 작업에 전달한다.

---

이 저장소를 기준으로 관리하는 모든 활성 하위 자동화 프로젝트가 공통 개발 규칙을 빠짐없이 따르도록 개선해줘. 분석이나 제안에서 끝내지 말고, 기존 구현과 지침을 확인한 뒤 필요한 코드·문서·테스트를 구현하고 검증해줘.

## 배경과 목표

최근 두 프로젝트를 ALM-QA-Automation으로 통합하면서 프로그램 구현·테스트·push는 수행했지만 상위 기준의 SPEC.md, CHANGELOG.md, progress.md 및 AGENTS의 SPEC workflow 적용이 누락됐어. SPEC 규칙 자체는 이미 있었지만 작업자가 놓쳤고 기존 검사도 이를 막지 못했어.

나는 신규 생성뿐 아니라 기존 프로젝트 작업, 프로젝트 통합·이름 변경·이동, 하위 src/apps 폴더에서 시작한 세션에도 같은 기준이 적용되길 원해. 에이전트가 규칙을 기억하는 것에만 의존하지 말고 누락을 진단하고 완료 전에 검출할 수 있게 해줘.

## 먼저 확인할 것

- 로컬 변경과 원격 main의 차이, 상위/프로젝트별 AGENTS·CLAUDE의 적용 관계.
- bootstrap/migration, 프로젝트 탐색, spec-lint, Bash·PowerShell 점검, publish/CI, 세션 시작 hook.
- 실제 적용 대상과 보관·일회성·제외 프로젝트. 다른 프로젝트의 비밀 설정이나 운영 데이터는 읽지 마.
- 기존 검사에서 의도적으로 허용한 INFO/WARN과 검사 누락을 구분해줘. 아래 진단도 현재 코드로 재확인해줘: SPEC 누락 INFO 통과, 바로 아래 akela.json 폴더만 탐색, workflow 문자열만 검사, Windows 점검은 kit-only, 인계 hook에는 SPEC readiness 확인 없음.

## 구현 요구사항

1. 공통 프로젝트 판별을 통일해줘. 명시적 프로젝트 경로 및 현재 작업 폴더에서 올바른 Root를 찾고, ALM-QA-Automation/apps/.../src에서도 통합 Root를 선택해야 해. Akela 사용 여부와 SPEC 적용 여부를 분리하고 별도 중첩 프로젝트 경계는 보존해줘.
2. 정확한 경로·활성/보관 상태·SPEC 적용 여부·명시적 제외 사유를 관리하는 단일 기준을 만들어줘. 신규·통합·이동 프로젝트가 누락되지 않게 하고 목록을 여러 파일에서 수동으로 중복 관리하지 않게 해줘. ALM-QA-Automation은 사용자가 확정한 이름이니 변경하지 말고 필요한 이름 예외를 지원해줘.
3. 프로젝트별 readiness 검사를 만들어줘. 활성 유지보수 프로젝트의 SPEC, CHANGELOG, progress, AGENTS 공통 workflow 및 CLAUDE 연결을 확인하고 누락·구버전·bootstrap 미완성·깨진 추적성을 구분해줘. 이 기준에 미달하면 완료/배포 검사에서 실패해야 해. 기존 advisory lint는 호환성을 유지해도 되지만 활성 프로젝트가 그것만으로 통과해서는 안 돼.
4. 공식 템플릿은 한 곳에서 관리하고 프로젝트 적용 버전을 확인해줘. migration은 기존 문서·사용자 지침·미커밋 변경을 보존하고 반복 실행해도 추가 변화가 없어야 해. SPEC 본문을 추측으로 채우거나 템플릿만 생성해 완료로 처리하지 마. 기존 사양과 코드가 다르면 SPEC / CODE MISMATCH로 남겨줘.
5. 기존 활성 프로젝트 전체를 진단하고 필요한 보완을 계획·적용해줘. 프로젝트별 사양은 해당 프로젝트의 코드·문서·테스트 근거로 작성해줘. 사실이 부족하면 확인 필요로 남기고 미준수 상태를 숨기지 마. 기능·인증·배포·예약 실행은 문서 체계 정리를 이유로 바꾸지 마.
6. PowerShell과 Bash에서 동일 대상에 같은 검사 결과가 나오게 해줘. 출력에 kit-only/project/workspace 범위, 발견·검사·제외·실패 수를 표시해줘. 검사기 오류·빈 대상·요약 누락을 성공으로 처리하지 마.
7. Codex와 Claude의 프로젝트/하위 폴더 시작 시 공통 기준·프로젝트 Root·SPEC 상태가 드러나게 해줘. SessionStart는 읽기 전용 안내로 두고, hook이 없거나 신뢰되지 않아도 독립 CLI와 완료/CI 검사가 동작해야 해. 실제 두 CLI에서 적용 여부를 확인하지 못했다면 미검증으로 보고해줘.
8. 별도 Git 저장소인 하위 프로젝트에도 검사가 적용되게 해줘. 키트 자체 검사나 루트 publish만 통과했다고 하위 프로젝트 준수를 선언하면 안 돼. 각 프로젝트에 적용 가능한 로컬/CI 검사 연결을 제공해줘.

## 보존 조건

- 기존 동작, 비밀값, 데이터, 사용자 수정과 Git 이력을 보존해줘. 삭제·history 재작성·전체 일괄 덮어쓰기는 하지 마.
- 공통 기준 예외는 사유와 적용 범위를 명시하고 조용히 건너뛰지 마. 보관본·일회성 도구는 명시적으로 분류해줘.
- 최신 기준을 강제하기 위해 관련 없는 lint를 약화하거나 검사 대상을 줄이지 마.
- 하위 저장소의 remote 변경·push·삭제는 이번 요청만으로 수행하지 마. 키트 저장소의 반영은 해당 AGENTS/publish 규칙을 따라줘.

## 검증과 완료 조건

누락 SPEC, workflow marker만 존재, 구버전 지침, bootstrap 문서, 없는 테스트 경로, 중첩 앱 cwd, Akela 없는 등록 프로젝트, 이동 후 낡은 경로, 한글·공백 경로, 사용자 승인 이름, 제외 프로젝트, hook 미설치, 검사기 실패를 테스트해줘. 잘못된 입력에서는 실패하고 수정 후에는 통과함을 확인해줘. migration 재실행과 사용자 파일 보존도 검증해줘.

완료 보고에는 변경 파일·검사 결과·검사한 프로젝트 목록과 수·보완 완료/미완료·제외 사유·운영 및 CLI 미검증 항목을 포함해줘. 다른 기존 작업 때문에 전체 검사가 실패하면 원인과 이번 변경의 결과를 분리해줘. 실제로 확인하지 못한 프로젝트까지 전부 준수한다고 말하지 마.

필요한 결정 중 저장소에서 확인할 수 있는 것은 먼저 조사하고, 중요한 모호성만 질문해줘.
