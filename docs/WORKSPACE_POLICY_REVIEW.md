# 하위 프로젝트 기본 규칙 적용 검토

검토일: 2026-09-21. 문서 보완 중 확인한 제안이며 워크스페이스 도구는 수정하지 않았다.

## 결론

상위 [automation-workspace](https://github.com/hongmin3/automation-workspace)의 SPEC 규칙은 이미 존재한다. 이번 누락의 직접 원인은 작업자가 상위 보충 지침을 확인하지 않고 하위 프로젝트 지침만 적용한 것이다. 별도로, 도구는 기존 프로젝트 호환성을 위해 일부 누락을 의도적으로 허용하므로 같은 실수를 자동으로 막지는 못한다.

로컬 워크스페이스 지침은 원격 main보다 일부 회귀 검사·macOS CI 안내 등이 앞서 있다. 아래 근거는 현재 로컬 파일 기준이며, 실제 키트 개선 전 원격과 로컬 변경을 먼저 대조해야 한다. SPEC 기본 규칙은 원격에도 존재한다.

## 확인된 공백과 개선

| 공백 | 코드 근거(키트 상대 경로) | 개선 제안 |
|---|---|---|
| SPEC이 없으면 검사 완료로 넘어갈 수 있음 | `tools/spec-lint.js`의 SPEC 미존재 INFO 후 반환; `scripts/check-workspace.sh`의 warning-only 허용 | 기존 lint 호환성을 유지하되 활성 유지보수 프로젝트용 readiness 게이트에서 SPEC/CHANGELOG/progress/AGENTS workflow를 필수화 |
| 탐색이 바로 아래 Akela 프로젝트에 제한됨 | `tools/spec-lint.js`의 `listProjects`; migration/sync 도구의 동일 탐색 | 공유 root resolver와 명시적 `--project` 지원; Akela 사용 여부와 SPEC 적용 여부 분리 |
| 구버전/불완전 workflow를 구별하지 못함 | migration과 lint의 `spec-workflow:` 문자열 존재 검사 | 관리 영역 버전·내용 hash 진단; 사용자가 추가한 지침은 보존하고 관리 영역만 갱신 |
| 직접 하위 폴더에서 시작한 세션의 사전 확인이 없음 | 인계 hook은 세션 인계만 담당 | 시작 시 공통 규칙→프로젝트 지침→SPEC 경로를 짧게 제시하는 읽기 전용 사전 점검; CI/완료 검사와 병행 |
| Windows 점검 범위가 이름보다 좁음 | `scripts/check-workspace.ps1` → `tools/check-kit.js` (kit-only) | `-Project`/`-IncludeProjects`를 별도 제공하고 실제 검사 범위·대상·제외 수 표시 |
| 통합/이동 후 프로젝트 목록이 낡을 수 있음 | 프로젝트 인덱스의 문자열 포함 여부 검사 | 정확한 경로·활성/보관·규칙 버전·제외 사유를 단일 등록부로 관리 |
| 사용자 지정 이름과 기본 이름 검사 충돌 | Bash workspace 검사에서 lowercase kebab-case 강제 | `ALM-QA-Automation` 이름은 유지하고 사용자 승인 예외를 명시 등록 |

## 권장 적용 순서

1. 등록부와 공유 root resolver: 활성 프로젝트를 빠짐없이 찾고, 앱 폴더 아래에서도 통합 프로젝트 Root를 선택한다.
2. 전체 읽기 전용 진단: 적용/누락/제외를 프로젝트별로 보고한다. 누락 프로젝트를 조용히 제외하지 않는다.
3. 기존 프로젝트 보완: 공식 migration으로 없는 파일·workflow만 추가하고 SPEC 내용은 프로젝트별 근거로 채운다. 템플릿 생성만으로 완료 처리하지 않는다.
4. 활성 프로젝트에는 strict readiness를 기본 적용한다. 레거시 advisory는 이행 기간 또는 명시적 보관/제외 프로젝트에만 남기고 사유를 표시한다.
5. 프로젝트별 완료·배포 검사와 CI에 readiness를 연결한다. 별도 저장소는 키트 루트 publish를 우회할 수 있으므로 각 프로젝트에도 검사 진입점이 필요하다.
6. SessionStart 안내를 보조로 붙인다. hook 미설치·미신뢰 상태에서도 독립 검사와 CI가 누락을 잡아야 한다.

공통 규칙은 한 곳에서 관리하되 프로젝트에 적용된 버전을 검사한다. 프로젝트 특수 규칙은 공통 필수 항목을 조용히 없애는 수단이 되어서는 안 된다. 충돌은 사용자 지시 우선, 명시적 예외와 이유를 남기는 방식으로 해결한다.

## 필요한 회귀 검증

- 활성 기존/신규/통합 프로젝트에서 SPEC 누락은 실패, 제외 프로젝트는 사유와 함께 집계.
- `apps/.../src`에서 시작해도 통합 Root 선택; 중첩된 별도 프로젝트는 경계 존중.
- Akela 없는 등록 프로젝트도 검사; 보관 폴더·복구 사본은 명시적으로 제외.
- marker만 있는 AGENTS/구버전/사용자 추가 지침을 구별; migration 재실행 시 사용자 파일 보존.
- PowerShell 5.1/7/Bash에서 같은 대상과 판정; 사용자 지정 이름 예외와 정확한 경로 검증.
- 누락된 검사기·실행 실패·빈 대상 목록을 통과로 처리하지 않음.
- 두 CLI의 루트/프로젝트/앱 하위 시작 세션을 실제로 시험하여 어떤 지침이 로드됐는지 확인.

이 제안은 모든 하위 프로젝트를 무조건 같은 내용으로 덮어쓰자는 뜻이 아니다. 공통 필수 기준의 누락을 검출하고 프로젝트별 기능 사양과 기존 변경을 보존하기 위한 것이다.
